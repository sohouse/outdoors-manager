# Development

## 目标

这份文档定义当前仓库的开发约定，帮助后续继续迭代时保持代码风格、分层习惯和最小验证要求的一致性。

## 开发原则

### 1. 先保证主链路清晰，再谈功能扩展

- 优先收紧边界，而不是继续堆功能
- 优先让代码可讲清楚，而不是只求“能跑”

### 2. 业务规则跟 service 走

- route 负责参数和边界
- service 负责规则和异常
- dao 负责数据库

### 3. 类型边界必须有运行时校验

- 不能只依赖 TypeScript
- query、body、response 边界优先考虑 schema

### 4. 权限控制以后端为准

- 前端权限分支只负责体验
- 真正的越权保护必须放在 service

## 目录与代码组织建议

### 页面层

- 页面容器只负责编排状态和调用动作
- 展示层组件尽量保持职责单一
- 复杂表单逻辑尽量独立组件

### API 层

- route 内优先先 parse 再调用 service
- 避免在 route 里堆业务判断
- 统一响应契约，不让不同接口各自返回不同 shape

### 业务层

- 业务函数命名应表达动作和边界
- 权限、owner、异常逻辑优先抽到共享 helper

### 数据层

- DAO 只做数据访问和必要映射
- 避免把业务异常判断大量下沉到页面或 route

## 前端调用约定

当前方向：

- 页面层逐步减少直接写 `honoClient + unwrapResponse`
- 每个模块优先补一层 API facade
- 错误弹窗和错误信息展示逐步走统一 provider

目标效果：

- 页面只关心成功后的后续处理
- API 解析和错误提示尽量横向复用

## 测试最小要求

新增或改造功能时，至少考虑下面三类风险：

- 输入是否合法
- 业务规则是否正确
- 关键错误分支是否可验证

推荐最小验证：

1. `pnpm type`
2. `pnpm test:unit`

如果改到了接口行为、权限边界或 response contract，应该补对应测试。

## 代码修改优先级

改一个功能时，建议按这个顺序：

1. 明确输入和输出边界
2. 明确 route / service / dao 各自职责
3. 处理错误模型和权限边界
4. 补最小验证
5. 最后再补文档或面试材料

## 不推荐的做法

- 在页面里直接堆大量 API 协议解析逻辑
- 用大量 `as` 把类型问题硬压过去
- 在多个页面重复实现相同错误弹窗逻辑
- 为了“扩功能”引入和当前主线弱相关的模块

## 当前最值得继续推进的改造

- 统一前端 API response 解析入口
- 统一页面错误提示切面
- 为重要改造补 plan 文档
- 把新文档体系接到实际开发流程里
