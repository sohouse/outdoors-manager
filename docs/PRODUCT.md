# Product

## 项目定位

Outdoors Manager 当前定位为一个偏 backend-leaning 的 TypeScript 全栈项目样本，而不是一个追求功能广度的成品平台。

它承载的核心目标是：

- 用更接近真实业务的场景训练全栈能力
- 用一个主模块讲清接口设计、权限边界、分层和工程化
- 把项目打磨成“可投、可讲、可深挖”的面试资产

## 当前阶段目标

当前阶段的第一目标不是继续大规模扩功能，而是把已有能力稳定、讲清楚、文档化。

当前最重要的产出是：

- 一个主链路完整的 Activity 模块
- 清晰的 auth / RBAC 设计
- 基础测试和 CI
- 成体系的项目讲述材料

## 已完成的主能力

- 用户注册与登录
- Better Auth 会话认证
- Hono middleware 注入认证上下文
- 基于 owner-aware RBAC 的读写权限控制
- Activity 列表、详情、编辑、删除
- 条件筛选与分页
- Prisma + PostgreSQL 数据访问
- 基础单元测试与 route 行为测试
- `lint + typecheck + unit test` CI

## 当前优先级

### P0

- 稳定主链路
- 补项目文档
- 提炼面试叙事
- 统一前端 API 调用与错误处理方式

### P1

- 把 Activity 模块的前端调用进一步抽成统一 API facade
- 统一页面错误提示和异步 action 模式
- 补更完整的架构文档和方案记录

### P2

- 扩展一个与当前业务强相关的新模块
- 例如订单、我的活动、车辆或领队管理

## 暂时不优先做的事

- 与当前业务主线弱相关的功能拼接
- 为了“看起来高级”而硬塞 AI / RAG 功能
- 大量 UI 翻新但不提升项目表达力的改动
- 一次性铺开过多新模块导致叙事失焦

## 产品与项目叙事原则

这个项目当前更适合这样表达：

- 它是一个从真实业务场景出发的全栈原型
- 它重点体现接口契约、权限控制、分层和工程化
- 它不是一个堆技术名词的 demo，也不是一个只做页面效果的前端项目

## 下一阶段建议

短期建议：

1. 收口现有功能改造。
2. 统一 API 返回解析和前端错误处理。
3. 补方案文档和剩余工作路线图。
4. 开始项目讲述和模拟面试。

中期建议：

1. 新增一个强相关业务模块。
2. 让权限、接口和数据流跨模块复用。
3. 让项目更像一个持续演进的系统，而不是单模块样本。
